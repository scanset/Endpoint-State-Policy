# Release Signing and Verification

This document describes how ESP releases are signed, what guarantees
the signatures provide, and how to verify them as a consumer.

## NIST SP 800-218 SSDF mapping

| SSDF Task | Implementation |
|---|---|
| **PS.2** — Verify software release integrity | Cosign signatures over every release artifact; SLSA v1 build provenance attached to each artifact |
| **PS.3.1** — Archive each release | GitHub Releases retain artifacts, signatures, and attestations for the project's lifetime |
| **PS.3.2** — Provenance data for components | CycloneDX SBOM shipped per release and individually signed |
| **PW.4.4** — Verify components meet security criteria | `cargo-auditable` embeds the dependency tree in every binary, enabling post-distribution `cargo audit bin` checks |

## What gets signed

For each tagged release (`vX.Y.Z`):

| Artifact | Signed | Provenance |
|---|---|---|
| Release archive (`*.tar.gz` Linux, `*.zip` Windows) | ✓ cosign keyless | ✓ SLSA v1 |
| CycloneDX SBOM (`*.cdx.json`, one per crate) | ✓ cosign keyless | ✓ SLSA v1 |
| Source code (the git commit pointed to by `vX.Y.Z`) | ✓ signed git tag | — |

Signatures and certificates ship alongside each artifact in the GitHub
Release. SLSA attestations live in GitHub's attestation API and are
retrievable via `gh attestation verify`.

## How signing works

ESP uses **[Sigstore](https://docs.sigstore.dev/) keyless signing**:

1. The release workflow (`.github/workflows/release.yml`) requests an
   OIDC identity token from GitHub.
2. Sigstore Fulcio issues an ephemeral signing certificate bound to
   that identity (the workflow file + commit SHA).
3. The artifact is signed with the ephemeral key; the signature plus
   a record of the issuance go to the public Rekor transparency log.
4. The ephemeral key is discarded.

**There is no long-lived signing key to steal or rotate.** Consumers
verify by checking that the certificate's identity matches the
expected workflow (i.e., the canonical ESP release workflow on the
`scanset` org).

Build provenance is generated by GitHub's `actions/attest-build-provenance`
action, which produces a SLSA v1 in-toto attestation tying the artifact
to the workflow run (repository, ref, commit SHA, build inputs).

## Verifying a release as a consumer

Prerequisites:

```bash
# Sigstore cosign 2.x
brew install cosign           # macOS
# or: https://docs.sigstore.dev/system_config/installation/

# GitHub CLI 2.x (for SLSA verification)
brew install gh
gh auth login
```

### 1. Verify SLSA build provenance

```bash
gh attestation verify esp-vX.Y.Z-x86_64-unknown-linux-gnu.tar.gz \
    --repo CurtisSlone/Endpoint-State-Policy
```

This confirms:
- The artifact was built by the official ESP release workflow.
- The build inputs (commit SHA, workflow file) match what was claimed.
- The attestation is logged in the GitHub attestation API.

### 2. Verify the cosign signature

```bash
cosign verify-blob \
    --certificate         esp-vX.Y.Z-x86_64-unknown-linux-gnu.tar.gz.crt \
    --signature           esp-vX.Y.Z-x86_64-unknown-linux-gnu.tar.gz.sig \
    --certificate-identity-regexp '^https://github.com/CurtisSlone/Endpoint-State-Policy/.+' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    esp-vX.Y.Z-x86_64-unknown-linux-gnu.tar.gz
```

This confirms:
- The signature was issued via Sigstore Fulcio.
- The signing identity was the official ESP release workflow.
- The signature is recorded in the public Rekor transparency log.

### 3. Verify the SBOM

The SBOM is signed the same way. After extracting the archive:

```bash
cosign verify-blob \
    --certificate         sbom/common.cdx.json.crt \
    --signature           sbom/common.cdx.json.sig \
    --certificate-identity-regexp '^https://github.com/CurtisSlone/Endpoint-State-Policy/.+' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    sbom/common.cdx.json
```

### 4. (Optional) Audit the binary for known vulnerabilities

Release binaries are built with `cargo-auditable`, which embeds the
dependency tree as compressed JSON. After installing
[`cargo-audit`](https://crates.io/crates/cargo-audit):

```bash
cargo audit bin esp-compiler
```

This scans the binary's embedded dep tree against the RustSec advisory
database — no source checkout required.

## Verifying the git tag

The git tag itself (`vX.Y.Z`) is signed by the release manager:

```bash
git tag --verify vX.Y.Z
```

The expected signing key is published as part of the SECURITY.md
profile for the ESP maintainers.

## Failure modes and what they mean

| Check | Failure says | Likely cause |
|---|---|---|
| `gh attestation verify` | "no matching attestations" | Artifact wasn't built by the official workflow — possibly a fork or a tampered upload |
| `cosign verify-blob` | "no matching signatures" or "certificate identity mismatch" | Signature missing, tampered, or signed by a different identity |
| `cosign verify-blob` | "rekor: entry not found" | Signature wasn't recorded in the transparency log — should never happen for an official release |
| `cargo audit bin` | "found N advisories" | Released binary depends on a crate with a now-known vulnerability — file an issue; release-patch decision |

Any verification failure for an official release should be reported
to `curtis@scanset.io` before using the artifact.
